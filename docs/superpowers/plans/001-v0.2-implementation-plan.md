# Valorant Statistical Coach v0.2 — Implementation Plan

Status: Phase 0 substantially complete. Phases 1–5 not started.
Source of truth for requirements: `SPECIFICATION.md` at the repository root.

---

## 1. Why this project exists

Public Valorant stat sites show raw aggregates. Self-coaching from them usually collapses into an arbitrary weighted score — `0.4*K/D + 0.3*ACS + 0.3*winrate` — whose weights are invented and which hides how few games the numbers rest on.

The specification's core principle is the opposite: each statistical method answers exactly one question, and uncertainty stays visible in the output. A 75% win rate from four games must read as four games.

The deliverable is a terminal tool that turns a public Tracker.gg match history into a coaching report where every claim carries a confidence interval, a sample count, and an explicit association-not-causation caveat. A local LLM phrases already-computed evidence; it never sees raw HTML and never invents a finding.

## 3. Decisions, and why

**Collection is a live Scrapling crawl of Tracker.gg.** Recorded plainly: `https://tracker.gg/robots.txt` sets `User-agent: *` with `Disallow: /*/profile/*` and `Disallow: /*/matches/*`, covering exactly the target pages, and specification §5.3 itself states Tracker Network does not permit scraping its sites. The user was shown this and reaffirmed the approach. The build therefore stays inside the specification's own limits — no stealth, no fingerprint spoofing, no proxy rotation, no CAPTCHA handling, no internal API calls, fail closed on any block — and the README carries a plain note that the tool requests paths `robots.txt` disallows and is intended for the operator's own profile.

**Local model is `qwen3:14b`.** 9.3 GB, 40K context, verified on the Ollama registry. Fits 12 GB fully on-GPU with roughly 2.5 GB left for KV cache, so no CPU offload. Chosen over `phi4:14b`, which matches it on reasoning but is English-centric and fails §8.1's French requirement, and over `gemma3:12b`, which has better French but weaker numeric reasoning over structured input. 24B-class models need ~14 GB at Q4 and would force the offload §8.1 tells us to avoid. Thinking mode is the deciding feature: the model's only input is a nested analysis JSON, and it needs to walk intervals and skip flags before answering. The user asked for a single best pick rather than a three-way benchmark, so §8.1's comparison step becomes one documented choice plus one measurement of that choice.

**Module layout is deliberately flat.** The `ponytail` plugin is now active in the harness and enforces a YAGNI ladder before any code is written. An earlier draft of this plan proposed ~22 files; that is speculative structure for a project this size, and specification §11 asks for "simple, testable components and clear interfaces over speculative abstractions". Nine modules, listed in §5, keep every real boundary while dropping the invented ones.

## 4. Build order, and why it is not the specification's order

The scraper is the only component whose success depends on a third party's markup and access controls. Everything else is deterministic.

So the deterministic core is built first against synthetic and fixture data, and the live scraper is wired in last behind an interface. The consequence is that a block or a DOM change can never leave the project with nothing working: the statistical engine, the fallback report and the acceptance criterion "the AI can be removed and the statistical report still remains useful" are all demonstrable without a single successful crawl.

## 5. Module layout

```
src/vcoach/
  __init__.py
  cli.py        typer app: run | collect | analyze | coach
  config.py     k=10, alpha=0.20, 2000 resamples, RNG seed, Ollama host, resolved model
  schema.py     field table + plausibility bounds + Riot ID parsing
  collect.py    MatchSource protocol, Scrapling source, snapshot source, raw archive, errors
  parse.py      profile page and match page selectors
  clean.py      cleaning, validation, data-quality report
  stats.py      all seven statistical methods + analyze()
  coach.py      Ollama client, prompt, five-section renderer, deterministic fallback
tests/
  fixtures/     saved HTML snapshots
docs/superpowers/plans/
data/
  raw/ clean/ analysis/
```

`schema.py` is the single source of truth for fields and bounds. The cleaner, the CSV writer, the quality report and the model's feature list all read from it, so they cannot drift apart.

`collect.py` holds the `MatchSource` protocol — `discover(riot_id, limit) -> list[MatchRef]` and `fetch(ref) -> RawMatch`. That protocol is the isolation boundary §5.2.5 requires: `clean.py`, `stats.py` and `coach.py` import nothing below it, so the scraping strategy can change without touching them.

## 7. Phase 1 — Contracts and CLI shell

`pyproject.toml` declares the `vcoach` console script and the dependencies above.

`schema.py` defines every field from §4.1–4.3 with its type and plausibility bounds: `HS% ∈ [0,100]`, `KAST% ∈ [0,100]`, `ADR` and `ACS` non-negative with generous upper caps, counts non-negative. It also parses `"Name#TAG"` once, builds the URL-encoded profile path `/valorant/profile/riot/{Name}%23{TAG}/overview` with the competitive list at `.../matches?playlist=competitive`, and derives the `Player_TAG` filename stem used across `data/raw`, `data/clean` and `data/analysis`. Every other module takes the parsed object, never a raw string.

`cli.py` stays thin: `run`, `collect`, `analyze`, `coach`, with `--matches`, `--model`, `--headed` and a `--no-think` flag that passes `think: false` to Ollama for a fast path. Reasoning stays on by default.

## 8. Phase 2 — Statistical engine

Test-first, RED → GREEN → REFACTOR, driven by synthetic samples with known answers. Every function is pure: arrays or a DataFrame in, JSON-serializable result out.

Existing library implementations are reused rather than hand-rolled:

| Spec | Method | Implementation |
|---|---|---|
| 7.1 | Wilson 95% interval | closed form; test asserts equality with `statsmodels.stats.proportion.proportion_confint(..., method="wilson")` |
| 7.2 | Jeffreys posterior | `scipy.stats.beta(w+0.5, l+0.5)` → `.mean()`, `.ppf(0.025/0.975)` |
| 7.3 | Empirical-Bayes shrinkage | `(wins_g + k*p_global)/(n_g + k)`, `k=10`; returns raw **and** shrunk side by side |
| 7.4 | Median/MAD robust z | `scipy.stats.median_abs_deviation`, then `0.67449*(x-median)/MAD`; guard `MAD == 0` |
| 7.5 | EWMA | `pandas.Series.ewm(alpha=0.20, adjust=False).mean()` |
| 7.6 | Cluster bootstrap | `numpy.random.default_rng(seed)`, resample whole matches 2000×, `np.percentile([2.5, 97.5])` |
| 7.7 | Regularized logistic | `sklearn` `Pipeline` + `ColumnTransformer` (`SimpleImputer` + `StandardScaler` on continuous, `OneHotEncoder(handle_unknown="ignore")` on map/agent) + `LogisticRegression(penalty="l2")`, `StratifiedKFold` + `cross_val_score(scoring="roc_auc")` |

The RNG seed is fixed in `config.py` so bootstrap results are reproducible across runs.

Behaviours the tests must pin down:

- Missing values never crash anything. Every function has a `NaN`-riddled input case.
- Fewer than 40 parsed win/loss matches, or only one class present, returns a structured `skipped` result naming the reason — not an exception, not a fitted model.
- Any bootstrap interval spanning zero is tagged `uncertain: true`, so neither the renderer nor the LLM can present it as a signal.
- `analyze()` always emits the §6.3 data-quality block (matches discovered, matches with a parsed result, per-stat completeness percentage) and the §7.7 leakage warning as a literal string field.

## 9. Phase 3 — Cleaning and data quality

Driven by `schema.py`: deduplicate on `match_id`; coerce numeric strings and `"23.4%"` forms; push implausible values to missing rather than trusting them; keep scraped K/D and computed K/D as separate columns; derive `opening_balance = FK - FD` and the binary win target; never infer `result` when the page gave no evidence; always carry `url` through for auditability.

Output is `data/clean/Player_TAG.csv`. The completeness report feeds both the analysis JSON and the confidence language in the coaching report.

---

## 10. Phase 4 — AI coach and deterministic fallback

`coach.py` holds four concerns that are small enough to live together:

- **Client.** `httpx` to `http://localhost:11434/api/chat`, health probe first. Any connection failure, timeout or missing model routes to the fallback. It is never fatal.
- **Prompt.** Carries the §8.4 guardrails verbatim — never invent a mistake absent from the data, distinguish association from causation, respect intervals and sample size, do not treat HS% as a universal aim score, do not treat K/D as the objective, recommend controlled experiments when evidence is weak — plus the §7.7 leakage warning. Input is the analysis JSON only, never raw HTML or scraped text.
- **Renderer.** Enforces the five-section contract: what the data actually says / what is probably noise / three coaching priorities / next 10-game experiment / what extra data would unlock better coaching. A missing section triggers one regeneration, then the fallback.
- **Fallback.** A deterministic template renderer over the same analysis JSON, producing the same five sections. This is what makes "the AI can be removed and the statistical report still remains useful" true rather than aspirational.

Both paths write `data/analysis/Player_TAG_coach.md`.

## 11. Phase 5 — Collection

`collect.py` implements the `MatchSource` protocol twice.

The **Scrapling source** uses `DynamicFetcher` / `DynamicSession` — real Playwright Chromium, headless by default, `--headed` for a visible window. `StealthyFetcher` is not used, because its fingerprint spoofing is excluded by §3.2, and `Fetcher`'s TLS browser-impersonation is avoided for the same reason. One session is reused across matches with a polite fixed delay between page loads.

The **snapshot source** parses saved HTML through Scrapling's selector API. Its real job is to be the test fixture loader so parser tests run offline and deterministically; it doubles as a manual escape hatch if live access is blocked.

`parse.py` uses Scrapling's adaptive selectors — `find_similar`, `find_by_text`, auto-relocation — so a class-name change does not immediately break the parser. Exact selectors are determined by inspecting the live pages during implementation, per §5.2. The match-detail URL shape must be confirmed then rather than guessed now.

The raw archive writes `data/raw/Player_TAG.json` plus an HTML snapshot for every fetched page **before** any parsing, so §3.1's reproducibility requirement holds and a parser fix never needs a re-crawl.

Errors are `BlockedError`, `PrivateProfileError`, `DomChangedError`, `MatchParseError`. Per-match failures are collected and reported, never fatal — §5.3 requires partial results over discarding the run. A `BlockedError` aborts cleanly with a message naming the likely cause: no retry escalation, no bypass attempt.

## 13. Verification

Each step is evidence for a §12 acceptance criterion. Run in order.

1. **Unit tests** — `pytest -v`. Must include the `NaN` cases, the `n < 40` skip, the single-class skip, the `MAD == 0` guard, and the Wilson-vs-`statsmodels` agreement check.
2. **Parser tests offline** — snapshot source over committed fixture HTML. Assert one full cleaned row, and assert that a deliberately damaged page raises `DomChangedError` instead of emitting fabricated values.
3. **Install check** — fresh venv, `uv pip install -e .`, `vcoach --help` resolves.
4. **Analyze without scraping** — feed a fixture `data/clean/Player_TAG.csv` to `vcoach analyze`; confirm the analysis JSON carries intervals, the quality block and the leakage warning.
5. **Small-sample behaviour** — same run with 4 matches. Assert a wide Wilson interval, a populated `skipped` field on the logistic stage, and no confident language anywhere in the report.
6. **Fallback path** — point the Ollama host at a dead port, run `vcoach coach`. A complete five-section `_coach.md` must still be produced.
7. **AI path** — with Ollama up and `qwen3:14b` loaded, run `vcoach coach`. Check the five sections hold and the guardrails survive contact with real numbers. Record VRAM resident (`ollama ps` — confirm 100% GPU, no offload), time to first token and tokens/sec in the README, per §8.1.
8. **End-to-end** — `vcoach run "YourName#TAG" --matches 50 --model auto`, then confirm all four artifacts exist under `data/`. If collection is blocked, the run must exit cleanly with a diagnostic and leave no partial-garbage CSV.

## 14. Known risks

- **Access.** Tracker.gg sits behind Cloudflare. Headless Chromium may be challenged, and the specification forbids doing anything about that. A blocked run is a legitimate, expected outcome — which is why Phases 2–4 land first and the offline fixture path exists.
- **Scoreboard depth.** Some match pages gate the full scoreboard. Fields that are not publicly rendered stay missing. The cleaner must not fabricate them, and the quality report will show the gap honestly.
- **Sample size.** §7.7 needs 40+ parsed matches with both classes. With fewer, the logistic stage reports `skipped` and the coach leans on §7.1–7.6. This is correct behaviour, not a bug.
- **Selector drift.** Adaptive selectors soften it but do not remove it. The raw HTML archive is what makes a parser fix cheap.
- **iCloud dehydration of the venv.** The project directory is an active iCloud sync root with no per-folder exclusion, so `.venv` will be synced and can be evicted. If imports start stalling or failing with what look like corrupt-file errors, that is the cause, not the code. Recovery is to delete `.venv` and recreate it — nothing is lost, the venv is disposable and git-ignored. Browser binaries and model weights already live on D:, so only the venv is exposed.
- **C: headroom recurs.** The iCloud log directory and AMD telemetry CSV will grow back. If C: tightens again, those are the first things to check, not the project.
